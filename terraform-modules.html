FIELD NOTE / TERRAFORM

How to reuse Terraform modules across environments

Development, QA, and production often need the same infrastructure pattern with different settings. Keep the shared resource definitions in a module and let each environment choose its inputs.

1. Give the module a clear purpose

A networking module might manage a VPC or VNet and its subnets. Pass address ranges, naming, and tags through typed variables. Return identifiers that other modules need, such as subnet IDs. If a change requires callers to supply a new input or changes an output, document what callers need to update.

2. Give each environment its own root configuration

One way to organize a repository is to keep a root module for each environment. Each root calls the shared module and has its own backend state. The directory layout alone does not isolate state, so explicitly configure distinct state paths and restrict access by environment.

modules/
  network/
    main.tf
    variables.tf
    outputs.tf
environments/
  dev/
  qa/
  prod/

3. Review the plan for the intended environment

Initialize and validate the chosen root, then review its plan. Check the target account or subscription and look at replacements, removals, and changes to network and access rules. If the plan includes an unexpected replacement, investigate before an apply. Treat saved plan files like state files because they can contain sensitive values.

cd environments/qa
terraform init
terraform validate
terraform plan

For shared changes, review plans for each affected environment and stage the rollout. A QA plan can help catch an issue early. A production plan still needs review against production’s own state and inputs.

References: HashiCorp’s guide to creating modules and the Terraform plan reference.
